The attack surface your SBOM can't see

Agent frameworks, MCP configs, system prompts in string constants, model names pinned in code, imports that don't exist: none of it is a package, so none of it reaches a scanner's inventory or an SBOM. Code scans now cover the AI surface -- and it's the same scan you already run.

Open a source tree from 2020 and you'd find source files, package manifests, and maybe a Dockerfile. Open one from this month and you'll also find a .mcp.json describing which external servers an agent may call, an AGENTS.md steering every coding agent that touches the repo, a .claude/ directory, system prompts embedded as string constants, and model names pinned in code. Our own product repo has all five. None of them are packages, so none of them appear in a software inventory. None of them are the language the scanners parse, so none of them appear in a finding. They are, mechanically, the most interesting attack surface in the repo: a tool registration with broad permissions is an authorization model living outside your identity system, a system prompt is code that executes on whatever the model does next, and a pinned model name is a dependency with a license and a vendor's terms attached.

No scanner inventories any of it. Not the incumbents, not the AI-native tools, and not ZeroQuarry -- until now. Code scans are getting an AI-surface pass: the inventory, injection leads, hallucinated-dependency detection, and a model-license export that come out of the scan you already run. This post is the release post, written before the code ships. Writing it first is a habit I picked up as a PM: the post is the spec the code has to keep up with, published early enough that we can't quietly descope it. Everything below is committed design.

What the inventory actually picks up

The first piece is an inventory pass that runs at scan time and records what the code calls, embeds, and delegates to: agent frameworks and LLM provider SDKs, MCP client and server configurations, skill and agent instruction files, system prompts embedded in code, tool registrations and their permission scope, and referenced model identifiers. The template for this already exists in the product: our infrastructure-as-code inventory works the same way, a deterministic pass that builds a picture the agent reasons about whether or not any rule fires.

Two kinds of cheap hygiene checks ride along, because the same pass sees them: auto-approve style flags in agent configs (the --yolo class, where an agent gets shell access and the config file says not to worry about it), and secrets that sit within reach of agent tooling. Those aren't vulnerabilities on their own. They're the kind of thing a reviewer wants flagged before the agent that reads the config is the same kind of agent that could abuse it.

The inventory lands as a durable artifact next to the scan report, and it feeds the coordinator's rubric, so the investigating agent reasons about the discovered surface even where no rule fires. If a repo wires up an MCP server with write access and a system prompt that instructs the agent to fetch URLs from user input, that connection should be visible to something that can reason about it instead of only to whoever happens to open the config file.

Prompt injection needs a producer, not a chat window

Prompt injection has sat at #1 on the OWASP LLM Top 10 since that list existed, and most of what ships to "scan" for it is a chat window where you paste code and an LLM opines. That approach drowns, because injection is a dataflow question: does untrusted content reach prompt construction, and does model or tool output reach a dangerous sink? The untrusted content classes are well understood (fetched web pages, file and document loaders, RAG chunks, issue and comment ingestion, third-party tool and MCP outputs). The dangerous sinks are the classics: exec, shell, SQL, HTML, eval. The chain between them is where the exploit lives.

Pure LLM scanning drowns in that chain and pure static analysis lies about it (the static tool will happily flag every place a string touches an LLM call, including the ten thousand that are harmless). This is exactly the shape our pipeline is built for: deterministic rules produce leads, a coordinator agent argues reachability and context, and adversarial validation attacks whatever survives (I wrote about what that review chain does to scanner noise earlier, in the out-of-band collector post and the AI-reviewed code study). The two rule classes we're shipping -- untrusted content reaching prompt construction, and model or tool output reaching dangerous sinks -- produce those leads for the first time. Until now the pipeline had no candidates for the #1 item on the LLM risk list. That was ours to fix.

Hallucinated dependencies, before the attacker registers them

When a coding model suggests an import that doesn't exist, that name sits in your code as a fact waiting to be weaponized: the attacker registers the package, and the next clean install runs their code. The research community gave this a name, slopsquatting, and it's the dependency-confusion problem all over again with a new generator of the names.

The check itself is mechanical: imports and references that don't resolve in the authoritative public registry become leads, never automatic findings. Not automatic, because an unresolved import is usually something boring -- a monorepo-internal package, a private registry artifact -- and a scanner that cries hallucination at every internal package gets muted. So the check carries a tenant allowlist for private registries and internal packages, and what's left after the allowlist is a small list of names worth a human's ten seconds. "Worth a human's ten seconds" is the bar the whole feature is tuned to; it's the same bar our SCA reachability confirmation applies before an advisory becomes a finding.

AIBOM: the dependency your manifest never captured

Ask a compliance team what models their product uses and watch what happens: someone greps the code for API keys, someone asks engineering, and the answer arrives as a spreadsheet that's stale by the next merge. Enterprise security questionnaires have started asking for a model inventory explicitly, and there's a reason the answer is hard: a pinned HuggingFace model or a hardcoded provider-model reference is a real dependency, with a license and provider terms (does the provider train on your inputs? what's the retention? what are the output-use restrictions?), and no dependency manifest captures it.

The standards now exist to make this an export instead of a PDF: CycloneDX has an ML-BOM profile and SPDX 3.0 has an AI profile. We're adding a curated registry of model licenses and provider terms beside the existing license pipeline (the one that normalizes npm/PyPI/crates licenses into SPDX expressions), and exporting through the existing SBOM machinery. The discipline carries over too: unknown stays unknown, never guessed, the same conservative normalization our SPDX alias table uses. A model card that doesn't state a license ships as "license unknown", not as a cheerful default.

Authorship detection is a guess with a dashboard

While we were designing this, an adjacent market was born: vendors claiming to detect whether code was written by AI, complete with percentages. Watch what that product does when you test it. A human who writes in the same idiom breaks it. A detector trained on last year's models breaks on this year's models. The false-positive rate never survives contact with a real repository. Authorship is a fact about history, and the artifact in front of you cannot prove facts about history. A vendor selling authorship detection is selling the guess.

What's checkable is better anyway: what the code calls, what it embeds, what it delegates to, and whether the failure patterns AI introduces are present -- a dependency that doesn't exist, untrusted input reaching a prompt, an agent config more permissive than anyone would defend in review. Those are facts about the artifact. If a scanner demo shows authorship percentages, the question that ends the pitch is: what does it say when a human writes the same pattern?

How it ships

One design decision above all the rest: this is a capability of the existing code scan, not a new module, scan type, or SKU. You run a source scan the way you already do; the AI surface inventory, the injection leads, and the hallucinated-dependency checks run inside it; findings land in the report tagged so you can filter them; the AIBOM download sits beside the SBOM download. Reports get an AI surface section and a coverage-card addition so "did you scan for what AI introduces?" has an artifact as an answer.

Shipping is in three phases: detection first (inventory, injection rule pack, hallucinated-dependency check), then the compliance artifact (AIBOM export), then the report surface and docs. The code for the first pieces is in development now; I'll update this post as each lands. Phase ordering can slip. The inventory can't, because the report surface and the findings tagging both read from it, so it goes first.
